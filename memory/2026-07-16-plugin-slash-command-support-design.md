# Design: Plugin And Workspace Slash Commands

Generated by office-hours on 2026-07-16
Status: DRAFT
Mode: Builder

## Problem Statement

AiFetchly should support Claude-Code-style slash commands from installed plugins and from workspace-local configuration. Users should be able to type commands in `AiChatV2`, plugin commands should become available when a plugin is installed, workspace commands should auto-load from the selected workspace, and workspace commands must be scoped to chats that selected that workspace.

## Current State

- The app already has a slash command stack: `SlashCommandModule`, `CommandRegistry`, `SlashCommandDispatcher`, prompt expansion, frontmatter validation, renderer suggestions, and `AiChatV2` dispatch.
- Plugin commands are already promoted from `<plugin>/commands/*.md` by `PluginComponentRegistryService.promotePluginCommandsAndAgents`.
- Workspace commands are already scanned from `.aifetchly/commands/*.md` by the workspace watcher and trust-filtered before registry mutation.
- The main gap is scoping: list and dispatch currently resolve against the registry without filtering by the active conversation workspace.
- The second gap is Claude compatibility: Claude plugin `commands` manifest declarations are carried opaquely, while AiFetchly promotion currently only scans a physical `commands/` directory.
- The third gap is install timing: plugin install invalidates runtime caches, but command promotion depends on the plugin registry apply/reload path.

## Premises

1. AiFetchly should not clone Claude's local/local-jsx command types initially; prompt commands are the safe MVP.
2. Workspace command visibility must be derived from `conversationId -> approved workspace -> sourceId`, not from renderer-provided workspace paths.
3. Plugin commands are global plugin capabilities; workspace commands are workspace capabilities. Do not copy plugin commands into workspace folders.
4. Built-ins must remain unshadowable. Workspace may shadow user, and plugin should stay lowest precedence.

## Approaches Considered

## Approach A: Scoped MVP

Summary: Keep the existing AiFetchly command format and command registry, but add conversation-aware filtering/resolution plus immediate plugin promotion after install.
Effort: M
Risk: Low
Pros:
- Smallest change with the biggest correctness gain.
- Reuses current registry, dispatcher, plugin promotion, workspace watcher, and trust filter.
- Fixes leakage of workspace commands into unrelated chats.
Cons:
- Claude manifest `commands` object/path compatibility remains partial.
- No command namespaces for plugins beyond current source badges.

## Approach B: Claude-Compatible Prompt Commands

Summary: Extend the existing plugin adapter/promotion layer to understand Claude's `commands` field, including `commands/` auto-detection, path arrays, object mappings, and inline content, while still producing AiFetchly `SlashCommandDefinition` prompt commands.
Effort: L
Risk: Medium
Pros:
- Best user experience for Claude plugin compatibility.
- Keeps execution safe: markdown becomes prompt expansion only.
- Plugin authors can reuse existing Claude command packs.
Cons:
- Requires more parser/validator work and stronger diagnostics.
- Needs careful name collision/namespace policy.

## Approach C: Full Claude Command Runtime

Summary: Rebuild command types around Claude's `prompt`, `local`, and `local-jsx` model, including local execution, command-specific allowed tools, model overrides, shell interpolation, and model-invocable skills.
Effort: XL
Risk: High
Pros:
- Maximum compatibility with Claude Code.
- Enables richer command workflows later.
Cons:
- Much larger security surface.
- Conflicts with current AI gate, tool approval, and Electron trust boundaries.
- Not necessary for the requested user workflow.

## Recommended Approach

Choose Approach B, implemented in two phases:

1. First implement Approach A's scoping and install-timing fixes.
2. Then add Claude-compatible prompt-command loading.

This preserves the existing architecture while making the feature feel complete for plugin authors.

## Implementation Outline

1. Add a command scope resolver in the main process that maps `conversationId` to the active approved workspace via `WorkspaceModule.getActiveWorkspace`.
2. Add scoped command list/lookup methods that include built-in, user, plugin, and only the active workspace sourceId.
3. Thread `conversationId` from `AiChatV2` into `AiChatV2Composer`, then into `listSlashCommands`.
4. Change `SlashCommandDispatcher` to resolve commands through the same scoped lookup.
5. After plugin install/import/toggle/reload, call the existing plugin component promotion path so command registry updates immediately.
6. Extend Claude plugin adaptation to expose command declarations instead of leaving them only in `__claudeOpaque__`.
7. Extend plugin command promotion to support `commands/` directory, manifest path/string/array declarations, object mappings, and inline content.
8. Keep command execution prompt-only for now: no shell execution, no local JSX, no automatic tool grants.

## Open Questions

- Should plugin commands be named `/review` with source badge only, or namespaced as `/plugin-name:review`? The safer long-term default is namespaced aliases plus optional short-name winner by precedence.
- Should workspace commands shadow plugin commands? Current rank says yes: built-in > workspace > user > plugin. That seems correct.
- Should plugin command diagnostics be surfaced in Plugin Detail UI, `/status`, or both?

## Next Steps

1. Fix conversation-aware list and dispatch scoping first.
2. Add tests that workspace commands appear only in chats with that workspace selected.
3. Add immediate plugin command promotion after install/import.
4. Add Claude `commands` manifest compatibility once scoping is safe.

## What I Noticed

The codebase is already halfway through this feature. The important work is not inventing a slash-command system; it is closing the scoping and compatibility gaps without widening the execution security surface.
