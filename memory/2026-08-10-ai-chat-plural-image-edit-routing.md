# DEBUG REPORT: Plural Image Edits Use `attach_local_images`

- **Symptom:** For requests such as “please modify the background color of those image in the workspace to white,” the coordinator discovered workspace images but called `attach_local_images` in groups. The first call attached only three images and the second was rejected by the per-request attachment limit, so the remaining images were not edited.
- **Root cause:** `ToolLoadPolicyService` classified both `attach_local_images` and `process_artifact_batch` as contextual for plural image-edit intent. Because the attachment tool description strongly recommends attaching images for edits, the provider could select it instead of the batch workflow. `AIChatQueryLoop` also accepted multi-path edit attachments without enforcing the one-output-per-input requirement. Empty textual `tool_catalog_search` calls did not discover the batch tool and therefore could not correct the route.
- **Fix:** Added a shared plural image-edit intent classifier. The load policy now keeps `attach_local_images` deferred for batch edits while exposing `process_artifact_batch`; single-image edits and multi-image analysis remain valid attachment cases. Empty catalog searches during a plural image edit automatically select the batch tool. A query-loop guard rejects multi-image edit attachments before execution and directs the model to call `process_artifact_batch` once with all exact paths and bounded concurrency.
- **Evidence:** The focused AI-chat regression suite passed 6 files / 78 tests. The complete main-process suite reached 417 files / 3,694 tests passing; afterward, its watch mode reran because of a transient SQLite `true/scraper.db-shm` path and reported an unrelated `ENOENT` watcher error.
- **Status:** DONE_WITH_CONCERNS — deterministic routing and regression coverage are complete, but the exact provider-driven flow was not exercised in a live Electron chat session during this run.
