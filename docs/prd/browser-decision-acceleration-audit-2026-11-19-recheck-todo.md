## Pending defects and requirements

### R01 — Provider admission, capability limits and dispatch (A01/A02, D-FR-01–05/08/09/14/16–19)

- [ ] Carry the admitted provider revision through dispatch, verification and approval retry. Check it after asynchronous preparation and at the mutation boundary. Use the admitted revision in the task journal. `ManagedBrowserAiToolService.ts:1528,1580,1660–1681,1705` now wires live revision checks and the captured chat configuration into decision calls. The runner still dispatches after intervening work without rechecking that epoch (`BrowserTaskRunner.ts:1100–1108,1260–1269,1694–1708`), and the admission metadata rereads the epoch (`ManagedBrowserAiToolService.ts:2094`). Cover provider changes during journaling, field resolution, approval and verification as well as during the original request.
- [ ] Distinguish unsupported, explicitly empty and legacy-unknown capability data. Apply `maxCandidates` and the configured request timeout. Validate the full input before transport and the full result before terminal/control/action branching. `BrowserTaskRunner.ts` still uses a wide fallback offer, special operation exemptions and targeted validation after early branches. The merged planner/caller criteria can exceed the wire limit of eight. Resume instructions can make the subgoal exceed 1,000 characters. Cover empty/failed/slow discovery, per-candidate operations, all untargeted and control operation branches, and legal inputs combined at their limits.

### R02 — Exact SELECT identity (A03, D-FR-12/15/17, D-AC-04)

- [ ] Require a trusted option identity and matching live state before dispatch. The runner now indexes values by the option's position in the filtered ID list, but can omit the expectation for a missing value (`BrowserTaskRunner.ts:1816–1829`). The worker resolves a value and calls `select` in a separate browser operation (`BrowserActionExecutor.ts:163–184,421–453`), so equal-valued options do not preserve the selected option's exact identity and the DOM can change between validation and commit. Cover blank and missing expectations, duplicate labels and values, single and multi-select, filtered earlier options and a change during the commit boundary.

### R13 — Approval loop, reference lifetime and uncertain effects (A18, D-FR-08/09/10a/15a/26/27, D-AC-05/06)

- [ ] Consume an approval exactly once when the authorized action is dispatched. The in-job wait consumes it (`ManagedBrowserAiToolService.ts:1090–1103`), then the runner redispatches (`BrowserTaskRunner.ts:1685–1708`) through the gate that consumes it again (`ManagedBrowserAiToolService.ts:787–806,1325–1344`). The second check can issue a fresh prompt and the redispatch also skips the normal intent/outcome callbacks. Verify the service and runner together through one approval and one dispatch, including denial, expiry, Stop and changed context.
- [ ] Pin the exact observation during inference and approval, and release that same pin on resolution. Inference has no corresponding pin; approval sends an unawaited pin and later unpins the latest observation (`BrowserTaskRunner.ts:520–555`, `ManagedBrowserAiToolService.ts:796`, `ManagedBrowserModule.ts:469–473,1245`). Bind approval to trusted semantic context and issuing observation/revision, while permitting passive same-target reobservation. Targeted context remains null in the fingerprint and consumption only requires a matching digest and a non-null initial revision (`ManagedBrowserAiToolService.ts:2374–2379`, `ManagedBrowserModule.ts:1266–1322`).
- [ ] Keep ownership until worker settlement and classify effect per command. The step timeout races ahead of abort settlement, samples a session-wide asynchronous progress flag and can release ownership (`ManagedBrowserAiToolService.ts:1793–1832,2145`, `ManagedBrowserModule.ts:323,1382,1832`). Navigation marks dispatch locally without the same progress update (`BrowserActionExecutor.ts:593–605`). Untargeted dispatch can throw before writing an unknown outcome (`BrowserTaskRunner.ts:1049–1052`), unlike the targeted catch. Test the same before/after-dispatch timeout, cancellation, worker failure and no-replay cases for targeted and untargeted operations.
