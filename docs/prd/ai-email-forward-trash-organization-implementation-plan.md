# AI Email Forwarding, Trash, and Organization — Implementation Plan

- Branch: `feature/email-forward-trash-organization` (git worktree `../aiFetchly-email-org`, cut from `dev`)
- Implements: [PRD](./ai-email-forward-trash-organization-prd.md) / [Technical design](./ai-email-forward-trash-organization-technical-design.md)
- Scope: **Stage B (release milestones M1–M5)** — single-message forward with attachment selection, single-message Trash and restore, durable operations, tool/IPC/UI integration. Stage C (M6: search + bulk) is explicitly deferred.

## Codebase findings that shape the plan

1. `imapflow`'s `messageMove` **silently falls back to COPY + `\Deleted` + EXPUNGE when the server lacks the MOVE capability** (verified in `node_modules/imapflow/lib/commands/move.js`). The adapter must check `connection.capabilities.has("MOVE")` before every move and refuse otherwise. No fallback is permitted.
2. imapflow fetches `source` via `BODY.PEEK` (`node_modules/imapflow/lib/commands/fetch.js`) — full-source retrieval never sets `\Seen`. Still asserted via adapter tests on the constructed fetch query.
3. `messageMove` returns `{ path, destination, uidValidity?, uidMap? }`; `uidMap` may be absent (no COPYUID) → record remote completion with unresolved destination UID and reconcile; never resend.
4. Received messages persist only parsed/sanitized bodies — raw source must be re-fetched from the server. `providerFolder`/`providerUidValidity` already exist on `EmailReceivedMessageEntity`; namespaced provider UIDs (`imap:<folderHash>:<uidValidity>:<uid>`) already encode folder+validity.
5. The reply stack provides the proven reliability patterns to mirror (not reuse): one-time hashed approval token, conditional claim `UPDATE … WHERE status=…` + unique idempotency key, `In(matchStatuses)` terminal fence, `replyWriteMutex` transaction wrapper, typed error codes, `requestCorrelationId` correlation.
6. `ImapEmailReceiveClient` has an `imapFlowFactory` test seam — the new mailbox adapter copies this seam so protocol tests use a deterministic fake connection instead of a live server.
7. SMTP: `OutboundSmtpSession` accepts any nodemailer `SendMailOptions` (multiple recipients, attachments) with TLS-mode retry; `info.accepted`/`info.rejected` give per-recipient outcomes the reply stack ignores. Per-install encryption key: `userSecretKeyService.getKey()` (AES-256-GCM, `FieldCipher` is string-only, so the artifact store adds a binary GCM helper).
8. Tools: built-ins register in `skillsRegistry.ts`; request-scoped confirmation = `confirmationPolicy: "request_scoped_action"` (refuses generic auto-approval in `evaluateToolApproval`); scheduled hard-block = `SCHEDULED_LOOP_ALWAYS_BLOCKED_TOOLS` (checked before the `full_access` fast path). AI-gated IPC = `registerAiValidatedHandler` (AI check before schema parse); manual controls use `registerValidatedHandler` — both share services/authorization.
9. DB: entities register in `src/config/dbEntities.ts`; `synchronize: true` creates tables in prod and tests. Migration = additive table + idempotent startup backfill (`legacy_unverified` locations); no destructive schema change in this release (the existing `(emailServiceId, providerUid)` unique index is kept; namespaced UIDs already encode folder+uidValidity; legacy bare-UID rows stay `legacy_unverified` and are ineligible for mutation).
10. UI: buttons belong in `emailreceive/detail.vue` (header actions) and `list.vue` (row actions); dialogs follow `OutboundEmailReviewDialog.vue`; chat cards follow `AiChatEmailReplyReviewCard.vue`; i18n keys under `emailOrganization.*` in all six language files.

## Key invariants enforced in code (from technical design §4)

- Verified location (`state = "verified"`, fresh UIDVALIDITY) is a precondition for every remote mutation; `legacy_unverified` rows are read-only.
- `pending → claimed` CAS + attempt row persist **before** any network I/O; only the claim winner proceeds.
- Duplicate invocations resolve to the existing operation via unique idempotency key; never a fresh send/move.
- Unknown outcomes (`outcome_unknown` / `needs_reconciliation`) block automatic replay; reconciliation only.
- Forward never touches `replyStatus`/`isAnswered`/processed state; trash/restore never expunges.
- No token/credentials/paths in tool args or AI-visible results; authorization originates from trusted UI/request provenance and is consumed exactly once.

## Deviations (documented, safe)

- **Additive migration instead of table-rebuild**: the design's controlled uniqueness-constraint removal is deferred; namespaced provider UIDs already encode folder+uidValidity, so the old unique index does not conflate folders. Legacy bare-UID rows are marked `legacy_unverified` and cannot authorize mutation (AC-21 satisfied).
- **No push progress channel in Stage B**: single-message operations complete within the request; the operation card polls `operation:get` on mount/reconnect. (Design §8.2 progress events remain a Stage C item.)
- **Sent-copy tracking starts at `not_requested`**: initial release reports "Submitted; Sent copy unavailable" (design §9.4 explicitly permits this).
