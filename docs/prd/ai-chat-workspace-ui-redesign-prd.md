## 1. Executive Summary

AiFetchly will replace its docked, header-heavy AI Chat V2 interface with a workspace-oriented desktop experience built around three coordinated regions:

1. A persistent left sidebar containing global navigation, workspaces, and the conversations associated with each workspace.
2. A focused center conversation area that renders only the selected conversation.
3. A collapsible right inspector for artifacts, execution activity, and context details.

The redesign must fix both information-architecture and runtime-performance problems. The current chat surface places conversation status, goals, scheduled loops, context usage, voice controls, compaction, history, MCP management, new-chat actions, deletion, and task management in one header. This makes the most frequently viewed area visually noisy and mixes controls with different scopes.

The redesign will remove the robot icon and the generic `AI Assistant` title. The center header will use the actual conversation title and show only one summarized execution state, a right-inspector toggle, and an overflow menu.

The redesign will also separate visible UI from background execution. AiFetchly must not create one Electron renderer process per conversation. The application window will use one trusted renderer for the application shell and selected conversation. Background conversation runs will continue through main-process coordination and bounded utility or worker execution. Inactive conversations will receive only lightweight summary updates in the renderer. Detailed streaming events will be delivered only for the selected conversation.

HTML generated by `create_html_artifact` and future artifact-producing skills will appear in the right inspector. Untrusted HTML will remain isolated from the trusted application renderer through a strict sandbox. The preview may use a separately isolated rendering surface when needed, but AiFetchly must not create or retain one preview renderer per artifact.

This PRD defines the product behavior, control placement, state model, process boundaries, performance requirements, security constraints, accessibility expectations, migration plan, and acceptance criteria for the redesign.

## 2. Background and Current State

### 2.1 Current layout

The current application uses a route-oriented main area and a resizable AI Chat V2 dock. AI-generated HTML artifacts can replace the route content while the chat remains in the dock.

The current chat header includes or exposes:

- A robot icon and `AI Assistant` title.
- Plan status.
- Active goal status and stop action.
- Active scheduled-loop status and pause, resume, and stop actions.
- Context usage.
- Spoken-response toggle.
- Conversation compaction.
- Conversation history.
- MCP tool management.
- New conversation.
- Clear conversation.
- Agent task list.

The composer already includes several controls that are correctly scoped to message creation, including attachments, mode, model, tool-approval mode, voice input, send, and stop.

### 2.2 Existing architectural foundations

The current implementation already provides useful building blocks:

- `ChatV2ConversationSummary` represents conversation-list data separately from full message history.
- `ChatV2RuntimeStatus` represents authoritative main-process runtime state.
- `ChatV2HistoryResponse` returns history and runtime status for one conversation.
- `AIChatConversationTurnCoordinator` prevents conflicting interactive and scheduled turns in the same conversation.
- `AIChatConversationUpdateBroadcaster` emits narrow refresh hints after durable persistence.
- Scheduled-stream events carry conversation and run identifiers for strict routing.
- AI artifacts are persisted through Model and Module layers.
- Artifact HTML renders in an iframe with an empty sandbox and no referrer.

The redesign should extend these foundations rather than build an unrelated second chat architecture.

### 2.3 Current problems

#### Visual hierarchy

The header mixes global, conversation, run, and composer controls. Frequent and infrequent actions receive similar visual weight. Long goal titles and scheduled-loop controls can consume most of the horizontal space.

#### Navigation

Conversation history is opened through a dialog instead of being a persistent part of workspace navigation. Users cannot easily scan active work across workspaces or see which background conversations need attention.

#### Renderer workload

A renderer that retains or reacts to many complete conversations can become slow because it must maintain message DOM, Vue reactivity, Markdown rendering, syntax highlighting, attachments, tool events, and streaming updates that may not be visible.

#### Execution ownership

If visible Vue components are treated as the owners of chat execution, switching conversations or reloading the renderer risks losing live state or coupling task completion to UI lifetime.

#### Artifact placement

Artifacts currently replace the route content. The new workspace design needs artifacts beside the conversation so the user can continue the conversation while inspecting or refining output.

## 3. Problem Statement

AiFetchly users may run several long conversations across different workspaces. Some conversations generate tokens, execute tools, wait for permission, run scheduled loops, or create artifacts while the user works elsewhere.

The product must allow this work to continue without rendering every conversation and without hiding important state in a crowded header.

The redesign must answer four questions clearly:

1. Where is the user now?
2. Which conversations are active or require attention?
3. What is the selected conversation doing?
4. Where can the user inspect and control detailed execution or artifacts without losing the conversation?

## 4. Product Principles

1. **One visible conversation, many independent tasks.** Only the selected conversation is rendered in detail. Background runs continue independently.
2. **Controls live where their effect occurs.** Global controls belong in navigation or settings. Message controls belong in the composer. Run controls belong near run status. Infrequent conversation actions belong in an overflow menu.
3. **The header orients, not manages.** The center header identifies the conversation and summarizes state. It does not become a toolbar for every feature.
4. **Status is progressive.** The sidebar provides awareness, the selected header provides summary, and the conversation or inspector provides detail.
5. **Persistence is authoritative.** Renderer state is a cache and presentation layer, not the source of truth for messages or completed runs.
6. **Inactive work stays lightweight.** Background conversations send summary updates, not token-by-token UI events, to the application renderer.
7. **Untrusted output stays isolated.** Generated HTML never runs with trusted renderer, Electron, Node.js, filesystem, or unrestricted network privileges.
8. **Context survives navigation.** Switching away from a running conversation does not stop it, lose its transcript, or redirect the user when it completes.
9. **Space is earned.** Persistent UI elements must serve orientation, immediate action, or ongoing awareness.
10. **Existing capabilities remain available.** The redesign must preserve plan mode, goals, scheduled loops, recovery, voice, provider selection, permissions, agent tasks, attachments, artifacts, workspace memory, slash commands, and at-mentions.
11. **Conversation content is semantic, not diagnostic.** Tool and plan surfaces explain outcomes, progress, and required decisions in user language. Raw arguments, result bodies, and lifecycle history belong in expandable details or Activity.
12. **One domain object has one evolving presentation.** A tool execution or plan changes state in place instead of producing visually disconnected call, result, approval, and completion cards.

## 5. Product Decisions

The following decisions are requirements, not open implementation choices:

1. The application will not create one Electron renderer per conversation.
2. One trusted application renderer will own the main navigation, workspace list, selected conversation, composer, and inspector controls for each application window.
3. Only the selected conversation will mount its detailed message view.
4. Running conversations will continue as main-process-coordinated background jobs when not selected.
5. The canonical transcript and durable run results will live outside the visible conversation component.
6. The renderer will receive detailed live events only for its selected conversation.
7. The renderer will receive lightweight summary and attention events for inactive conversations.
8. Background execution will use bounded concurrency. It will not create an unlimited process or worker per run.
9. One conversation will not execute conflicting turns concurrently. Existing per-conversation turn coordination remains required.
10. The center header will not display a robot icon or the text `AI Assistant`.
11. The center header will use the actual conversation title, with `New chat` as the untitled fallback.
12. The header will contain no more than conversation identity, one summarized status, inspector toggle, and overflow menu.
13. Conversation history will move from a modal dialog into the workspace-aware left sidebar.
14. `create_html_artifact` results will open in the right inspector by default.
15. The right inspector will be collapsible and resizable on wide screens and an overlay or full-width view on narrow screens.
16. Generated HTML will remain sandboxed. No redesign requirement may weaken the existing artifact security boundary.
17. Workers and utility processes will never access the database directly. They will send typed events to the main process.
18. IPC handlers will not access TypeORM repositories directly. Database work will remain in Model and Module classes.
19. AI IPC entry points will check the appropriate AI enablement policy before parsing or executing an AI request.
20. All new or modified user-facing text will be translated in English, Chinese, Spanish, French, German, and Japanese.
21. Tool calls and matching results will render as one evolving execution row keyed by tool-call identity, not as separate generic `Tool Call` and `Tool Result` cards.
22. Related tool executions from one assistant response will form a compact execution group in the conversation; complete technical execution records will live in Activity.
23. Plan generation, clarification, approval, revision, execution, and completion will use lifecycle-specific surfaces rather than one large all-purpose plan card.
24. The conversation will show concise plan summaries and required decisions. Activity will show the complete rendered plan, versions, changes, affected scope, execution history, and technical details.
25. `Approve plan` will be the primary approval action, `Request changes` will be secondary, and permanent discard or rejection will be an infrequent action rather than an equally prominent default.

## 6. Goals

1. Make switching between large conversations feel immediate.
2. Keep background conversations running independently of visible Vue components.
3. Make workspaces and their conversations continuously discoverable.
4. Show running, waiting, completed, unread, failed, cancelled, and interrupted states without header clutter.
5. Reduce renderer memory and rendering work as conversation count grows.
6. Preserve a focused reading and writing surface in the center.
7. Keep frequently used composition controls close to the composer.
8. Keep run-specific controls close to the active run.
9. Place artifacts and detailed execution information in a stable secondary surface.
10. Preserve every existing AI Chat V2 capability through the migration.
11. Maintain secure Electron process boundaries and artifact isolation.
12. Recover correctly after renderer reload, application restart, worker failure, or operating-system sleep.

## 7. Non-Goals

The first release will not:

1. Create a browser-style tab for every conversation.
2. Keep every conversation component mounted but hidden.
3. Create one operating-system process per chat or per artifact.
4. Replace the existing AI model, provider, or tool execution protocol.
5. Move database access into renderer, IPC, utility, or worker code.
6. Allow cloud execution after the desktop application has completely exited.
7. Build real-time multi-user collaboration.
8. Build a general-purpose IDE layout or file editor.
9. Turn the right inspector into a second global navigation system.
10. Render arbitrary assistant text as trusted HTML.
11. Allow generated artifacts to access Electron APIs, Node.js APIs, local files, cookies, local storage, unrestricted network resources, or top-level navigation.
12. Remove current features solely to simplify the redesign. Existing features must be relocated or deliberately deprecated through a separate product decision.

## 8. Users and Core Use Cases

### 8.1 Marketing operator

Runs scraping, campaign, contact, or email tasks in several workspaces. The user needs to see which conversation is still running and inspect results without opening every chat.

### 8.2 Power user

Uses plan mode, goals, scheduled loops, tools, local providers, and artifacts. The user needs dense functionality without a toolbar that dominates the conversation.

### 8.3 Casual user

Starts one conversation, sends attachments, and reads the answer. The interface should not require understanding goals, context windows, MCP tools, or worker execution.

### 8.4 Long-running-task user

Starts a job, switches to another workspace, and returns later. The first job must keep running, show an accurate state in the sidebar, and mark its result unread without changing the selected conversation.

### 8.5 Artifact user

Asks `create_html_artifact` to create a report or dashboard. The artifact opens beside the conversation and remains available while the user requests revisions.

## 9. Information Architecture

### 9.1 Wide-screen structure

```text
┌──────────────────────┬────────────────────────────────┬──────────────────────┐
│ Global navigation    │ Conversation header            │ Inspector             │
│                      │                                │ Artifacts Activity     │
│ New chat             ├────────────────────────────────┤ Context                │
│ Search               │                                │                      │
│ Automations          │ Selected conversation          │ Selected artifact or │
│ Customize            │                                │ execution details    │
│                      │                                │                      │
│ Workspaces           │                                │                      │
│ ▾ Workspace A        │                                │                      │
│   ● Running chat     │                                │                      │
│   • Unread result    │                                │                      │
│   Failed chat        ├────────────────────────────────┤                      │
│ ▸ Workspace B        │ Contextual run strip           │                      │
│                      │ Composer                       │                      │
│ Account / Settings   │                                │                      │
└──────────────────────┴────────────────────────────────┴──────────────────────┘
```

### 9.2 Layout regions

#### Left sidebar

The left sidebar has three vertical zones:

1. Fixed global navigation.
2. Independently scrollable workspace and conversation hierarchy.
3. Fixed account, settings, or connection state.

The workspace list must not push global navigation or account controls off-screen.

#### Center conversation

The center contains:

1. Minimal conversation header.
2. Virtualized message history for the selected conversation.
3. Inline permission, question, plan, error, and artifact cards.
4. Optional contextual run strip.
5. Composer.

#### Right inspector

The inspector contains three primary tabs:

- **Artifacts**: HTML, images, documents, generated files, versions, copy/export actions.
- **Activity**: current tools, goals, plans, scheduled loops, agent tasks, progress, run history, failure details.
- **Context**: workspace, attached files, at-mentions, memory status, context usage, compaction information.

The inspector must remember its open or closed state and width per application window. The selected tab may be remembered globally or per conversation, but artifact auto-open must select the Artifacts tab.

## 10. Left Sidebar Requirements

### 10.1 Global navigation

The top section contains:

- New chat.
- Search.
- Automations.
- Customize.

MCP tool management belongs under Customize or Settings, not in the conversation header.

### 10.2 Workspace hierarchy

Each workspace row must support:

- Expand and collapse.
- Workspace name with truncation and full-name tooltip.
- Workspace-level running or attention count when useful.
- Context menu for workspace-specific actions.
- A clear selected state.

Each conversation row must show:

- Conversation title.
- Relative last-activity time when space permits.
- One compact state or attention indicator.
- Selected state.
- Unread state.
- Context menu.

The initial list may show a limited number of recent conversations per workspace with a `More` action. Search must be able to find conversations outside the initially rendered subset.

### 10.3 Sidebar state vocabulary

| State | Indicator | Meaning | Required action |
| --- | --- | --- | --- |
| Queued | Clock or hollow progress indicator | Waiting for an execution slot | Optional cancel through details |
| Running | Animated spinner | Actively generating or using tools | None unless user opens chat |
| Awaiting permission | Lock or approval indicator | Cannot continue without a decision | Draw attention and make selectable |
| Awaiting user | Question or pause indicator | Needs user input | Draw attention and make selectable |
| Completed unread | Accent dot | New result arrived while inactive | Clear when conversation is viewed |
| Failed unread | Warning icon | Run failed while inactive | Clear attention after user reviews error |
| Cancelled | Muted stop icon | User or system cancelled the run | No action required |
| Interrupted | Recovery icon | App or worker stopped before completion | Offer retry or recovery in conversation |
| Idle | No persistent icon | No active or unread state | None |

A spinner must not be the only state representation. Icons require accessible names, and state must not depend on color alone.

### 10.4 Sidebar behavior

1. Selecting a conversation changes the center view but does not stop any other run.
2. Completion of an inactive conversation updates only its summary and unread indicator.
3. Background completion must not navigate the user away from the selected conversation.
4. Workspace and conversation expansion state must survive renderer reload.
5. The sidebar must support keyboard navigation through global items, workspaces, and conversations.
6. Large workspace lists must use incremental rendering or virtualization.
7. Search results must identify both workspace and conversation.

## 11. Minimal Conversation Header

### 11.1 Required content

```text
┌─────────────────────────────────────────────────────────────────────┐
│ Conversation title                     ● Running · 2 tools    ◧  ⋯ │
└─────────────────────────────────────────────────────────────────────┘
```

The header may contain only:

1. Conversation title.
2. Optional workspace breadcrumb when the sidebar is collapsed or the title would otherwise be ambiguous.
3. One summarized conversation or run state.
4. Inspector toggle.
5. Overflow menu.

### 11.2 Removed content

The header must not contain:

- Robot icon.
- `AI Assistant` title.
- Conversation history button.
- New conversation button.
- MCP tool manager.
- Spoken-response toggle.
- Model selector.
- Mode selector.
- Tool-approval selector.
- Full goal objective and controls.
- Full scheduled-loop details and controls.
- Dedicated context chip with detailed token counts.
- Clear or delete button.
- Agent task list button.

### 11.3 Conversation title

1. An untitled conversation displays `New chat`.
2. AiFetchly may generate a title after the first meaningful exchange.
3. The user can rename the conversation through the overflow menu or direct title interaction.
4. Long titles truncate without changing header height.
5. The full title is available to assistive technology and through a tooltip.

### 11.4 Summarized status

The status uses one short phrase, for example:

- `Queued`.
- `Running`.
- `Running · 2 tools`.
- `Waiting for approval`.
- `Waiting for your answer`.
- `Failed`.
- `Completed`.

Clicking or focusing the status opens the Activity inspector when details exist.

### 11.5 Overflow menu

The overflow menu contains infrequent conversation-level actions:

```text
Rename chat
Compact conversation
Export conversation
Duplicate conversation
────────────────────
Clear messages
Delete chat
```

Requirements:

1. Destructive actions appear in a separated section.
2. Clear and delete require confirmation when data loss would occur.
3. Clearing an active scheduled loop must preserve the existing stop-or-confirm safety behavior.
4. Global settings and MCP management must not appear in this menu.

## 12. Center Conversation Requirements

### 12.1 Selected conversation only

Only the selected conversation mounts a detailed message view. Switching conversations must:

1. Unsubscribe from detailed live events for the previous conversation.
2. Preserve or save the previous conversation draft and scroll position.
3. Load the next conversation's persisted history and runtime status.
4. Subscribe to detailed events for the new conversation.
5. Restore the new conversation's draft and scroll position when available.
6. Never stop either conversation solely because selection changed.

### 12.2 Message rendering

1. Long histories must use message virtualization or incremental windowing.
2. The renderer should initially mount only the visible message region plus a small buffer.
3. Older messages load on demand when the user scrolls upward.
4. Code highlighting, large images, reasoning panels, and complex tool results should render lazily when visible.
5. Incomplete streamed content may use lightweight Markdown processing.
6. Full Markdown normalization and syntax highlighting should occur after completion or when a block becomes stable.

### 12.3 Streaming updates

The UI must not perform a full reactive update for every tiny token chunk.

1. Detailed chunks for the selected conversation may be buffered for approximately 40 to 80 milliseconds or one animation frame before a Vue update.
2. Completion, error, permission, user-question, and cancellation events bypass unnecessary delay.
3. Buffered content must flush before terminal events.
4. Speech output may consume its own stream, but it must remain bound to the correct selected conversation and run.

### 12.4 Inline cards

The following remain in the conversation flow or pinned immediately above the composer when they require a user decision:

- Tool permission request.
- Plan question.
- Plan approval.
- Workspace required or trust decision.
- Recoverable error.
- Artifact card.
- File-operation summary.

Completed decision cards return to normal message history after resolution.

### 12.5 Tool execution groups

Tool activity in the conversation must read as part of the assistant response, not as internal diagnostic messages.

1. A tool call and its matching result form one evolving execution row associated by tool-call identity.
2. The row changes from queued or running to completed, failed, cancelled, interrupted, or waiting without appending a second generic result card.
3. Related rows from one assistant response are grouped into one execution stack with aggregate progress such as `2 of 3 complete`.
4. The primary label uses a human-readable action such as `Searching project files` or `Creating HTML report`.
5. The raw tool name, such as `create_html_artifact`, is secondary monospace metadata when it helps expert users.
6. Arguments, raw structured results, logs, and full timing details are collapsed by default and available through Details or Activity.
7. Running groups remain expanded. Successful historical groups may collapse to one summary row.
8. Permission, user-input, failure, and unresolved recovery states never collapse automatically.
9. Specialized outputs replace the generic result body: artifacts use artifact cards, files use file summaries, images use image output, and permissions use decision cards.
10. If legacy history cannot reliably pair a call and result, it uses a compact standalone execution receipt instead of inventing a relationship.

Example:

```text
Execution                                      2 of 3 complete
────────────────────────────────────────────────────────────
✓ Analyze project files                         18.4s
✓ Compare import workflows                       7.2s
◌ Create visual report                         Running
```

### 12.6 Plan lifecycle presentation

A plan is one durable domain object with state-specific presentation:

```text
Drafting
  -> Needs clarification
  -> Ready for review
  -> Changes requested
  -> Approved
  -> Executing
  -> Completed, failed, cancelled, or interrupted
```

Requirements:

1. Only the latest unresolved plan decision is prominent in the conversation.
2. Drafting and executing use the run strip plus compact execution or progress rows.
3. Clarification uses a pinned question flow.
4. Awaiting approval uses a concise plan decision card.
5. Approved, changes-requested, discarded, and completed states collapse to durable receipts in history.
6. Previous versions, prior answers, decisions, full plan content, and execution history remain available in Activity.
7. The UI must not append another full-size plan card for every lifecycle transition.

### 12.7 Plan approval card

The awaiting-approval card contains:

- `Plan ready for review` or an equivalent localized decision heading.
- Plan title and concise objective.
- Version as secondary metadata.
- Authoritative step count, affected-file count, risk, or impact only when those values exist.
- Two or three important steps or a short `Changed since vN` summary.
- `Review full plan`, which opens the plan detail view in Activity.
- Primary `Approve plan` action.
- Secondary `Request changes` action.
- Infrequent `Discard plan` or rejection action in overflow when supported.

The conversation card must not contain a long nested scrolling plan document. Approval must not require trusting a truncated summary: the complete plan and its version are available before approval through Activity.

### 12.8 Plan clarification and revision

1. Multiple clarification questions use a focused one-question-at-a-time flow with progress such as `1 of 3`.
2. Single-select and multi-select semantics remain explicit.
3. Option rows include concise descriptions when the trade-off is not self-evident.
4. Users can move backward before final submission.
5. Consequential multi-question flows provide an answer review before submission.
6. Required questions remain inline or pinned above the composer even when the inspector is closed.
7. Submitted questions collapse to a receipt such as `Answered 3 planning questions`; answers remain available in Activity.
8. `Request changes` opens one focused feedback field with optional prompt suggestions such as reduce scope, add validation, or clarify migration.
9. After feedback submission, the conversation shows a compact `Changes requested · Creating plan vN` receipt and progress state.
10. Reject and request-changes flows remain separate only when they have materially different durable semantics.

## 13. Composer and Contextual Run Strip

### 13.1 Composer controls

The composer owns controls that affect the next message:

- Attach files.
- Plan or Build mode.
- Model selection.
- Tool-approval mode.
- Voice input.
- Spoken-response preference or a compact voice menu.
- Send.
- Stop the selected active response.

The composer should remain usable when the inspector is open. Controls may collapse into a compact menu on narrow center widths, but Send and Stop remain directly accessible.

### 13.2 Context usage

Context usage moves beside the model or context control in the composer. The default representation is a small ring or compact indicator. Clicking it opens the Context inspector with:

- Used and total tokens.
- Percentage.
- Compaction state.
- Workspace memory state.
- Attached or mentioned context.
- Compact-conversation action when permitted.

### 13.3 Contextual run strip

The run strip appears immediately above the composer only when relevant:

```text
┌─────────────────────────────────────────────────────────────┐
│ ◌ Running goal: Analyze competitor sites          Stop  › │
├─────────────────────────────────────────────────────────────┤
│ Ask a follow-up…                                            │
│ [＋]  Build ▾  Model ▾                               [■]   │
└─────────────────────────────────────────────────────────────┘
```

It may represent:

- Active goal.
- Active plan.
- Active or paused scheduled loop.
- Current tool chain.
- Waiting for permission.
- Waiting for user input.
- Recoverable failure.

Requirements:

1. The strip shows one primary status, one primary action when applicable, and a disclosure action.
2. Full details and secondary controls open in the Activity inspector.
3. The strip disappears when no special run state exists.
4. The strip must not permanently reduce message space for idle conversations.
5. Goal and scheduled-loop control behavior must remain consistent with their existing PRDs.

## 14. Right Inspector

### 14.1 General behavior

1. The inspector is collapsible.
2. It is resizable on wide screens with reasonable minimum and maximum widths.
3. Closing the inspector does not close, delete, or stop the selected artifact or run.
4. Reopening restores the last relevant tab unless a newly created artifact requests immediate opening.
5. The inspector shows data for the selected conversation unless clearly labeled as global.
6. The inspector must not become a second place to browse all conversations.

### 14.2 Artifacts tab

The Artifacts tab supports:

- Artifact list for the selected conversation.
- Current artifact preview.
- Title, type, description, created time, and version.
- Copy HTML where permitted.
- Export through approved application-level tools.
- Open previous versions.
- Close preview without deleting the artifact.
- Regenerate or request revision through the conversation.
- Loading, missing, invalid, blocked, and failed-preview states.

When `create_html_artifact` returns `openImmediately: true`, AiFetchly opens the inspector, selects Artifacts, and displays that artifact. If the user is viewing another conversation when an inactive conversation creates an artifact, AiFetchly marks the originating conversation unread but does not replace the current inspector content or navigate away.

### 14.3 Activity tab

The Activity tab displays:

- Current run and queue state.
- Tool execution groups, individual calls, arguments, safe result details, progress, timing, and errors.
- Goal objective, iteration, evidence, and verification state.
- Full rendered plan document, current state and version, prior versions, changes between versions, prior clarification answers, approval or revision decisions, affected scope, risks, validation, and execution progress.
- Scheduled-loop state, next run, limits, pause, resume, and stop actions.
- Agent tasks and cancellation actions.
- Recovery attempts.
- Error details and retry actions.
- Start, update, and completion timestamps.

### 14.4 Context tab

The Context tab displays:

- Active workspace.
- Workspace trust status.
- Workspace memory status.
- Attached documents and images.
- At-mentioned files.
- Pasted-text references.
- Used and available model context.
- Compaction state and action.
- Provider or model limitations relevant to the conversation.

## 15. Control Placement Matrix

| Existing control or status | New location | Rationale |
| --- | --- | --- |
| Robot icon | Removed | Product context already identifies the experience |
| `AI Assistant` | Replaced by conversation title | Users need conversation identity, not a generic label |
| New conversation | Left sidebar | Global navigation action |
| Conversation history | Workspace conversation list | History is persistent navigation, not a modal utility |
| Search conversations | Left sidebar search | Applies across workspaces and conversations |

## 16. Conversation and Run State Model

### 16.1 Separate conversation from run

A conversation is a durable container. A run is one execution attempt inside that conversation.

```typescript
interface ConversationSummary {
  conversationId: string;
  workspaceId: string | null;
  title: string;
  lastActivityAt: string;
  preview: string;
  unread: boolean;
  attention: "none" | "permission" | "user_input" | "failure";
  runtimeStatus:
    | "idle"
    | "queued"
    | "running"
    | "awaiting_permission"
    | "awaiting_user"
    | "completed"
    | "failed"
    | "cancelled"
    | "interrupted";
}

interface ChatRun {
  runId: string;
  conversationId: string;
  owner: "interactive" | "scheduled" | "goal" | "agent";
  status:
    | "queued"
    | "running"
    | "awaiting_permission"
    | "awaiting_user"
    | "completed"
    | "failed"
    | "cancelled"
    | "interrupted";
  createdAt: string;
  startedAt?: string;
  finishedAt?: string;
}
```

These interfaces describe the required product semantics. A technical design may extend existing types rather than introduce these exact names.

### 16.2 State rules

1. `queued` means accepted but not assigned an execution slot.
2. `running` means a provider, tool, or agent is actively working.
3. `awaiting_permission` means execution cannot continue without a permission decision.
4. `awaiting_user` means execution cannot continue without an answer or approval.
5. `completed` means a terminal result was durably persisted.
6. `failed` means a terminal error was durably persisted and no automatic recovery remains.
7. `cancelled` means the user or system intentionally stopped the run.
8. `interrupted` means process loss or restart prevented a clean terminal result.
9. `unread` is separate from runtime status.
10. A completed inactive conversation becomes `completed + unread`; selecting it clears unread after its new result is loaded.

## 17. Electron Runtime Architecture

### 17.1 Process model

```text
┌──────────────────────────────────────────────────────────────────┐
│ Trusted application renderer                                     │
│ Sidebar + selected conversation + composer + inspector controls  │
└────────────────────────────┬─────────────────────────────────────┘
                             │ Typed IPC commands and subscriptions
┌────────────────────────────▼─────────────────────────────────────┐
│ Electron main process                                            │
│ Chat coordinator + subscription router + worker-pool scheduler   │
│ Module layer + persistence orchestration                         │
└───────────────┬───────────────────────┬──────────────────────────┘
                │                       │
                │ Typed job/event IPC   │ Module -> Model
                │                       │
┌───────────────▼──────────────┐  ┌─────▼─────────────────────────┐
│ Bounded utility/worker pool   │  │ SQLite / TypeORM persistence │
│ AI, tools, browser, CPU work  │  │ Conversations, runs, output │
│ No direct database access     │  │ Main process only            │
└───────────────┬──────────────┘  └───────────────────────────────┘
                │
                │ Validated artifact metadata
┌───────────────▼──────────────────────────────────────────────────┐
│ Sandboxed artifact rendering surface, created lazily             │
│ No Node.js, Electron APIs, same-origin privilege, or navigation   │
└──────────────────────────────────────────────────────────────────┘
```

### 17.2 Trusted application renderer

The renderer owns presentation only:

- Current navigation selection.
- Selected conversation cache.
- Lightweight conversation summaries.
- Drafts and scroll positions.
- Open inspector tab and width.
- Batched presentation of selected-run events.

It does not own:

- Durable transcripts.
- Background run lifetime.
- Worker allocation.
- Database connections.
- Authoritative completion state.
- Artifact security validation.

### 17.3 Main-process chat coordinator

The coordinator must:

1. Validate start, stop, subscribe, unsubscribe, retry, and control commands.
2. Check AI enablement before executing AI work.
3. Persist the user message and run record through Module and Model layers.
4. Enforce same-conversation turn coordination.
5. Place accepted work into the correct bounded queue.
6. Assign jobs to eligible utility or worker capacity.
7. Receive typed progress and terminal events.
8. Persist durable output before broadcasting completion hints.
9. Route detailed events only to renderer subscriptions for the correct conversation and run.
10. Route summary events to the sidebar store.
11. Reconcile active and interrupted runs after restart.

### 17.4 Worker responsibilities

Workers or utility processes may:

- Call AI providers.
- Execute isolated tools.
- Perform CPU-heavy parsing or transformation.
- Run browser automation when assigned to an appropriate pool.
- Emit structured progress, partial output, artifact metadata, completion, failure, and cancellation events.

Workers or utility processes must not:

- Access TypeORM or SQLite.
- Call Electron renderer APIs.
- Decide which conversation is selected.
- Broadcast directly to windows.
- Read or mutate global UI state.
- Create unbounded nested processes.

### 17.5 Renderer count requirement

For one normal application window:

- One trusted application renderer is expected.
- Zero or one active isolated artifact preview renderer may exist when the chosen preview technology requires it.
- Closing the inspector should release or suspend expensive preview resources.
- Inactive conversations and inactive artifacts must not retain dedicated renderers.

## 18. Subscription and Event Routing

### 18.1 Subscription lifecycle

The renderer identifies one selected conversation per application window.

```text
Select conversation B
  -> unsubscribe detailed events for conversation A
  -> load B history and runtime state
  -> subscribe to B detailed events
  -> keep summary subscription for all visible workspace conversations
```

The main process may maintain a mapping equivalent to:

```typescript
Map<WebContentsId, ConversationId | null>
```

The exact implementation may differ, but routing must be enforced before sending high-volume events.

### 18.2 Detailed events

Detailed events include:

- Text and reasoning deltas.
- Tool-call deltas.
- Tool progress.
- Tool results.
- Plan state.
- Questions and approvals.
- Goal events.
- Recovery events.
- Usage updates.
- Generated images and artifacts.
- Terminal completion, error, and cancellation.

Detailed events require both conversation and run identifiers wherever multiple run types could overlap.

### 18.3 Summary events

Summary events for inactive conversations contain no prompt, response, tool result, secret, or artifact body. They include only data needed to update navigation, for example:

```typescript
interface ConversationSummaryEvent {
  conversationId: string;
  workspaceId: string | null;
  runtimeStatus: ConversationSummary["runtimeStatus"];
  attention: ConversationSummary["attention"];
  unread: boolean;
  lastActivityAt: string;
  runId?: string;
  reason:
    | "run_queued"
    | "run_started"
    | "permission_required"
    | "user_input_required"
    | "run_completed"
    | "run_failed"
    | "run_cancelled"
    | "run_interrupted"
    | "artifact_created";
}
```

The renderer reloads authoritative history when the user selects the conversation or receives a terminal update for the currently selected conversation.

### 18.4 Late and stale events

1. The renderer ignores detailed events whose conversation ID is not selected.
2. The renderer ignores events whose run ID is not the active compatible run for that conversation view.
3. Terminal persistence remains authoritative if live events arrive out of order.
4. Switching conversations clears only presentation buffers, not main-process execution state or shared listeners needed for summaries.
5. A worker event received after cancellation must not resurrect a terminal run.

## 19. Bounded Worker Pool

### 19.1 Default concurrency

The initial product default is three concurrent general AI/chat executions across the application. This is a starting policy, not a promise that all hardware or providers can sustain three.

The pool must support a configured range of one to three general executions in the first release.

### 19.2 Resource classes

Work should be assigned by resource class when necessary:

| Pool | Initial concurrency | Examples |
| --- | ---: | --- |
| General AI/API | 3 | Chat generation, lightweight tool coordination |
| Browser automation | 1 | Puppeteer scraping, authenticated browser tasks |
| CPU-heavy processing | Derived conservatively from CPU and memory | Parsing, media, large transformations |
| Artifact batch coordinator | Existing bounded policy, normally up to 3 | Per-item image or artifact operations |

One physical worker may support more than one compatible asynchronous run only if isolation, cancellation, and provider behavior remain correct. The product requirement is bounded work, not necessarily one worker process per active run.

### 19.3 Queue behavior

1. Accepted work receives a run ID immediately.
2. Work without capacity enters `queued` state.
3. The selected conversation may receive interactive priority over inactive scheduled work.
4. Existing same-conversation rules still prevent conflicting turns.
5. Scheduled occurrences may defer or coalesce according to their PRD rather than interrupt interactive work.
6. Cancelling a queued run removes it without starting a worker.
7. Cancelling a running run propagates an abort signal and records a terminal state.
8. Worker crashes free capacity only after the affected run is marked failed, recovering, or interrupted.
9. The queue must not starve scheduled or background work indefinitely. A technical design must define aging or fairness.

## 20. State Ownership and Persistence

### 20.1 Three state layers

#### Durable database state

Authoritative for:

- Workspaces and conversation association.
- Conversation metadata and title.
- Messages.
- Runs and terminal outcomes.
- Plans, goals, and scheduled-loop state.
- Artifacts and versions.
- Unread or last-read markers when they must survive restart.

#### Main-process runtime state

Authoritative while the application is running for:

- Active leases.
- Queue position.
- Worker assignment.
- Cancellation controllers.
- Live streaming buffers.
- Renderer subscriptions.
- Worker health.

#### Renderer cache

Temporary and replaceable:

- Visible messages for the selected conversation.
- Conversation summaries needed for the sidebar.
- Drafts.
- Scroll position.
- Expanded message details.
- Inspector state.

### 20.2 Visible component state

The selected conversation component may own only presentation details such as:

- Currently focused message.
- Expanded reasoning or tool section.
- Local scroll anchoring.
- Temporary composer UI.

Unmounting the component must not lose persisted messages, run state, permissions awaiting action, scheduled work, or generated artifacts.

## 21. Artifact Security and Lifecycle

### 21.1 Security requirements

Generated HTML must use a sandbox equivalent to or stricter than the existing artifact workspace:

- No Node.js integration.
- Context isolation enabled for any dedicated web contents.
- Sandbox enabled.
- No same-origin privilege.
- No top navigation.
- No popups.
- No forms that submit data.
- No arbitrary external scripts, stylesheets, fonts, tracking pixels, or network calls.
- No filesystem, Electron, shell, clipboard, cookie, or local-storage access from artifact content.
- No direct message channel to privileged application APIs.
- No `v-html` insertion into the trusted application DOM.
- Referrer suppressed.

### 21.2 Artifact lifecycle

1. Worker or tool produces validated artifact input.
2. Main process validates and persists through `AIArtifactModule` and its Model.
3. Tool result contains bounded artifact metadata, never the full artifact body in normal chat events.
4. Selected conversation renders an artifact card.
5. The inspector requests artifact content by ID.
6. The sandboxed preview displays the artifact.
7. Closing the preview preserves the artifact record.
8. Opening another artifact reuses the preview surface when safe.
9. Deleted, missing, invalid, or blocked artifacts show explicit states without crashing the conversation.

## 22. Core User Flows

### 22.1 Start a new workspace conversation

1. User selects `New chat`.
2. If a workspace is currently selected, the new conversation inherits it unless the user changes the workspace.
3. Center header displays `New chat`.
4. Composer receives focus.
5. User sends the first message.
6. Main process creates or resolves the durable conversation and run.
7. Conversation appears under the correct workspace immediately.
8. A generated title may replace `New chat` after the first meaningful exchange.

### 22.2 Switch away while a chat is running

1. Conversation A is running.
2. User selects conversation B.
3. A remains running and shows a sidebar spinner.
4. Detailed A events stop flowing to the renderer's center view.
5. B history loads and receives detailed events if B is active.
6. A completes and receives a completed-unread indicator.
7. The selected conversation remains B.
8. Selecting A reloads its durable final result and clears unread after display.

### 22.3 Background conversation requires permission

1. Conversation A requests permission while inactive.
2. Sidebar changes A to `Awaiting permission` with an attention indicator.
3. AiFetchly may show a non-disruptive application notification according to user settings.
4. It must not switch the selected conversation automatically.
5. Selecting A displays the pinned permission card and Activity details.
6. Grant or denial resumes or terminates the exact run.

### 22.4 Generate an HTML artifact

1. User requests a visual report in the selected conversation.
2. AI calls `create_html_artifact`.
3. Artifact is validated and persisted.
4. Chat shows an artifact card.
5. Inspector opens to Artifacts when `openImmediately` is true.
6. User continues chatting while the artifact remains visible.
7. A revision creates a new artifact version or related artifact according to the artifact PRD.

### 22.5 Renderer reload

1. Renderer starts or reloads.
2. It requests global navigation, workspace summaries, conversation summaries, and active run summaries.
3. It restores the selected conversation ID when valid.
4. It loads selected history and runtime state from the main process.
5. It subscribes to that conversation's detailed events.
6. Running background conversations reappear with correct sidebar states.
7. No run is cancelled merely because the renderer reloaded.

### 22.6 Full application restart

1. Main process starts and initializes persistence.
2. Durable runs marked non-terminal are reconciled.
3. Resumable scheduled work follows its existing recovery policy.
4. Non-resumable interactive work becomes `interrupted` or a more specific recovery state.
5. The sidebar must not show permanently running work with no owner.
6. The selected conversation offers retry or recovery where safe.

## 27. Performance Requirements

### 27.1 Renderer architecture

1. Conversation count must not increase renderer-process count.
2. Inactive conversation count must not increase mounted message-component count.
3. Only selected-conversation high-volume events may trigger message rendering.
4. Inactive conversations receive summary events only.
5. Completed execution groups should collapse without unmounting unresolved actions or creating a reactive update per hidden raw result field.
6. Full plan documents and prior versions load lazily in Activity rather than with every transcript page.

### 27.2 Interaction targets

The following are product targets measured on a representative supported development machine with local persisted data:

- Selection feedback appears within 100 milliseconds.
- A recently viewed cached conversation becomes readable within 200 milliseconds at the 95th percentile.
- An uncached local conversation history becomes readable within 500 milliseconds at the 95th percentile, excluding database migration or corruption recovery.
- Sidebar scrolling remains visually smooth with at least 1,000 conversation summaries through virtualization or incremental rendering.
- Streaming presentation updates occur no more often than once per animation frame and normally use 40 to 80 millisecond batching.
- Opening or closing the inspector does not restart the selected run or reload full conversation history.

These targets must be validated against an agreed fixture and adjusted only through an explicit performance review, not silently during implementation.

### 27.3 Memory targets

1. Switching conversations must release heavy DOM and preview resources from the previously selected conversation.
2. Renderer memory growth must be bounded when repeatedly switching among a fixed set of conversations.
3. Closing an artifact preview must release its document and expensive media resources.
4. A soak test must demonstrate that repeated switching and streaming does not produce unbounded memory growth.

## 28. Reliability and Recovery Requirements

1. Every run reaches a durable terminal or recoverable state.
2. Renderer destruction does not implicitly cancel background runs.
3. Worker exit is detected and associated runs are failed, retried, or interrupted according to policy.
4. Cancellation is idempotent.
5. Duplicate terminal events do not create duplicate assistant messages or artifacts.
6. Persisted completion occurs before the summary event that marks a result available.
7. The renderer can reconstruct selected-conversation state from persistence after missing any number of live events.
8. Late events cannot overwrite a newer run or resurrect cancelled work.
9. Scheduled loops retain their persistent scheduler semantics and do not rely on a mounted renderer.
10. Permission and user-question states survive conversation switching and renderer reload.

## 29. Security and Privacy Requirements

1. Renderer IPC payloads must be validated and sanitized.
2. Detailed events are routed only to the subscribed selected conversation.
3. Summary events contain no prompt content, assistant content, secrets, raw tool results, API keys, or artifact bodies.
4. Worker messages use explicit discriminated unions and reject unknown message types.
5. Workers cannot access database APIs.
6. IPC handlers cannot access database repositories directly.
7. AI enablement is checked before AI request parsing or provider calls.
8. Provider API keys remain outside renderer responses.
9. Artifact validation and sandboxing remain mandatory.
10. External links from chat or artifact metadata open through a controlled external-navigation policy.
11. Workspace trust and tool permission decisions remain scoped to the correct conversation, workspace, task, and run.
12. Switching conversations must not leak drafts, attachments, context, speech, tool output, or artifact data across conversation IDs.

- Conversation selection latency.
- History load latency and message count.
- Renderer message-mount count.
- Stream chunks received versus UI flushes.
- Detailed events dropped because the conversation or run was stale.
- Summary event count.
- Queue wait time.
- Run duration by resource class.
- Worker count and worker restarts.
- Artifact preview creation and disposal.
- Renderer memory snapshots in development or diagnostics mode.
- Interrupted-run reconciliation outcomes.
- Tool pairing failures, legacy fallback count, group expansion, and semantic-result classification failures.
- Plan question, review, request-change, approval, discard, version-switch, and execution transitions using identifiers and bounded metadata only.

Logs must use identifiers and bounded metadata. They must not log prompts, assistant bodies, API keys, raw attachments, or artifact HTML by default.

- **FR-060**: A new plan version must identify meaningful changes from the prior version when change data is available.
- **FR-061**: Plan drafting and execution must integrate with the contextual run strip and tool execution presentation instead of creating competing status cards.
- **FR-062**: Plan status must not be redundantly displayed in the header, run strip, decision card, and status chip at the same level of detail.
- **FR-063**: Full plan review must support a resizable inspector on wide screens and a full-width or overlay surface on narrow screens.
- **FR-064**: Plan questions, decisions, receipts, and version navigation must be keyboard accessible, localized, and understandable without color.

## 33. Migration Strategy

The redesign should ship incrementally behind a feature flag until acceptance criteria pass.

### Phase 1: State and measurement foundation

- Add performance instrumentation for current selection, rendering, streaming, and memory behavior.
- Define normalized conversation summary, attention, unread, and run-state contracts.
- Ensure every live event carries adequate conversation and run identity.
- Preserve existing UI.

### Phase 2: Main-process ownership and subscriptions

- Introduce or formalize the chat coordinator.
- Move background run lifetime out of visible components.
- Add selected-conversation detailed subscriptions.
- Add lightweight summary subscriptions.
- Reconcile renderer reload and stale events.

### Phase 3: Bounded execution

- Route eligible work through bounded resource-class queues.
- Preserve existing batch coordinator limits.
- Add queue, cancellation, fairness, and worker-failure behavior.

### Phase 4: Workspace sidebar and selected-chat center

- Introduce workspace and conversation hierarchy.
- Move history and new-chat actions into the sidebar.
- Mount only the selected conversation.
- Add list and message virtualization.

### Phase 5: Minimal header and control relocation

- Remove robot icon and `AI Assistant`.
- Add conversation title and summarized status.
- Move controls according to the placement matrix.
- Add contextual run strip and overflow menu.
- Replace paired generic tool-call/result cards with evolving execution groups and specialized result surfaces.
- Replace the all-purpose plan card with plan summary, decision, question, receipt, and Activity-detail surfaces.
- Preserve tool-call identity, plan identity, plan version, and existing durable approval/question semantics through compatibility adapters.

### Phase 6: Right inspector and artifact migration

- Add Artifacts, Activity, and Context tabs.
- Move HTML artifacts from route replacement into the inspector.
- Preserve or strengthen sandboxing.
- Add responsive overlay behavior.

### Phase 7: Compatibility, accessibility, and i18n

- Verify every capability in the compatibility matrix.
- Complete keyboard, screen-reader, reduced-motion, and contrast checks.
- Complete translations in all supported languages.

### Phase 8: Performance validation and default rollout

- Run large-history, large-sidebar, multi-run, restart, and soak tests.
- Compare metrics with the current UI.
- Fix regressions.
- Make the redesign the default only after migration and rollback paths are validated.

## 35. Acceptance Criteria

The redesign is ready for default rollout only when all of the following are true:

1. The normal application window does not create a renderer per conversation.
2. Only the selected conversation has a mounted detailed message view.
3. At least three conversations can be queued or running while the user switches among them without losing execution state.
4. Inactive running conversations show accurate sidebar states without receiving token-by-token message rendering.
5. An inactive completion produces an unread indicator and never changes current navigation.
6. Permission, user-question, failure, cancellation, and interruption states are visually and programmatically distinct.
7. The header contains no robot icon or `AI Assistant` text.
8. The header contains only conversation identity, summarized status, inspector toggle, and overflow.
9. Every current header control is available in the destination defined by the placement matrix or has an approved deprecation decision.
10. The composer retains attachment, mode, model, tool approval, voice, Send, and Stop behavior.
11. The contextual run strip handles goals, plans, scheduled loops, waiting states, and recoverable failures without permanent clutter.
12. `create_html_artifact` opens securely in the right inspector for the selected conversation.
13. Artifact creation in an inactive conversation does not hijack the current inspector.
14. Generated HTML cannot access privileged application APIs or unrestricted external resources.
15. Renderer reload does not cancel active main-process-owned work.
16. Full application restart does not leave orphaned runs permanently marked running.
17. The bounded worker policy prevents unlimited concurrent processes or executions.
18. Same-conversation conflicting turns remain serialized.
19. Large lists and histories meet the agreed performance fixture targets.
20. Repeated switching and artifact preview use do not produce unbounded renderer memory growth.
21. Keyboard navigation and screen-reader labeling pass the accessibility test plan.
22. All new and modified strings are present in all six supported language files.
23. Existing plan, goal, loop, recovery, voice, attachment, permission, provider, memory, task, and artifact tests remain passing or are migrated with equivalent coverage.
24. Paired tool calls and results appear as one evolving row; raw details remain available without dominating the conversation.
25. Related tool rows group under one assistant execution summary, and unresolved states never disappear through automatic collapse.
26. Specialized artifacts, files, images, permissions, and errors do not receive a redundant generic result card.
27. Awaiting plan approval presents a concise decision card with access to the complete plan before approval.
28. Complete plans render in Activity with structured hierarchy, versions, changes, affected scope, risks, validation, and decision history.
29. Multi-question clarification is focused, keyboard operable, reviewable when consequential, and collapses to a durable receipt after submission.
30. Approved, revised, discarded, executing, completed, failed, cancelled, and interrupted plans remain distinguishable without duplicating the same status across surfaces.

## 36. Risks and Mitigations

| Risk | User impact | Mitigation |
| --- | --- | --- |
| Moving execution ownership exposes hidden renderer assumptions | Runs stop or lose events after switching | Introduce coordinator and subscription tests before UI migration |
| Summary and detailed events diverge | Sidebar state conflicts with conversation state | Persist first; treat summaries as hints; reload authoritative state |
| Too many statuses create new visual clutter | Sidebar becomes hard to scan | One indicator per row; progressive detail in header and inspector |
| Right inspector becomes overloaded | Users cannot find artifacts or run details | Three stable tabs with conversation scope and clear auto-open rules |
| Queue priority starves scheduled work | Monitoring tasks run late indefinitely | Define fairness or aging while preserving interactive priority |
| Stream batching makes output feel delayed | Chat appears less responsive | Keep batching within 40 to 80 ms and flush terminal events immediately |
| Virtualization breaks scroll anchoring or accessibility | Users lose reading position | Test upward loading, live append, keyboard focus, and screen readers |
| Artifact preview weakens isolation during redesign | Generated HTML reaches privileged APIs | Preserve empty sandbox baseline and add automated security assertions |
| Feature migration loses a current header action | Power-user regression | Use the compatibility and placement matrices as release gates |
| Multiple stores become competing sources of truth | Stale UI and duplicate messages | Database authoritative, main runtime authoritative for live work, renderer replaceable |
| Call and result events cannot always be paired in legacy history | Missing or misleading execution presentation | Pair only with stable identity; use compact standalone receipts when identity is absent |
| Compact tool rows hide information power users need | Reduced debuggability | Keep safe arguments, results, timing, and logs available through Details and Activity |
| Plan summary encourages approval without enough review | Users approve incomplete or risky work | Always provide complete versioned plan review before approval; keep summary metadata authoritative |
| Plan and question surfaces create another set of competing status chips | Visual clutter returns | Define one status owner per hierarchy level and collapse resolved transitions to receipts |

## 37. Trade-offs and Alternatives Considered

### 37.1 One renderer per conversation

**Rejected.** It provides isolation but scales Chromium memory, event loops, and rendering resources with conversation count. Background work does not require a DOM or renderer.

### 37.2 Keep all conversation components mounted but hidden

**Rejected.** It avoids reload work but retains message DOM, reactive subscriptions, Markdown output, syntax highlighting, and attachments for invisible chats.

### 37.3 Put every control in the right inspector

**Rejected.** The header becomes clean, but frequent message controls become distant or unavailable when the inspector is closed. Controls should follow scope.

### 37.4 Put every infrequent control in one overflow menu

**Rejected.** It hides global settings, active-run actions, and permission states behind an unrelated conversation menu.

### 37.5 Recommended contextual distribution

**Selected.** Global actions use navigation or Settings. Conversation maintenance uses overflow. Message configuration uses the composer. Active-run information uses a contextual strip and Activity. Artifacts and context use the inspector.

### 37.6 Continue replacing the main route with artifacts

**Rejected for the redesigned chat workspace.** It prevents the user from keeping the conversation and artifact visible together. The right inspector supports refinement workflows more directly.

### 37.7 Separate generic cards for every tool call and result

**Rejected.** It exposes implementation events as conversation content, duplicates tool identity, increases vertical noise, and separates an action from its outcome. One evolving execution row preserves causality and reduces clutter.

### 37.8 Keep the complete plan document inside every approval card

**Rejected.** Long nested scrolling cards make comparison, version review, responsive layout, and decision focus worse. The conversation owns the concise decision; Activity owns the complete versioned document.

## 40. Final Product Definition

The successful redesign is not merely a new visual shell. It is a change in ownership and hierarchy:

- Workspaces own conversation organization.
- The selected conversation owns the center reading and writing surface.
- The main process owns execution coordination and durable state transitions.
- Bounded workers own expensive or failure-prone background work.
- The sidebar owns cross-conversation awareness.
- The header owns identity and one-line orientation.
- The composer owns next-message controls.
- The contextual run strip owns immediate active-run control.
- Evolving execution groups own concise tool progress and outcomes in the conversation.
- The plan decision dock owns the latest required clarification or approval.
- Activity owns safe technical tool detail and the complete versioned plan lifecycle.
- The inspector owns artifacts, detailed activity, and context.
- The database remains the durable source of truth.
- The renderer remains a replaceable presentation client.

This separation allows AiFetchly to support many workspaces and concurrent conversations without turning conversation count into renderer count, header complexity, or lost background work.
