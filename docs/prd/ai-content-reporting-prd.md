## 1. Summary

AiFetchly presents text, images, plans, artifacts, email templates, keywords, and other content dynamically generated by AI in response to user input. Microsoft Store certification rejected the product because users cannot report inappropriate AI-generated output from within the app.

AiFetchly must add a clear **Report AI output** action wherever user-visible AI-generated content appears. The action opens a localized, accessible dialog that identifies the reported output, asks the user to choose a concern category, explains exactly what evidence will be sent, and submits a bounded report to the marketing backend. The user receives a durable report reference on success.

The reporting path is a safety and support function, not an AI-generation function. It must remain available when hosted AI is disabled, a subscription expires, the selected model is unavailable, or the original conversation is no longer active. It must never consume AI credits or call an AI model.

This release also adds the Store metadata and certification evidence needed to show compliance with Microsoft Store Policy 11.16: disclosure of live generative AI, an in-product reporting mechanism, and an operational review path.

## 2. Policy Requirement

Microsoft Store Policy 11.16 requires products with dynamic content created by generative AI in response to user input to:

1. disclose live generative AI in Store metadata;
2. disclose live generative AI in Partner Center during submission;
3. ensure generated content complies with applicable Store policies; and
4. provide a means for users to report inappropriate content to the developer, followed by appropriate developer action.

Policy source: `https://learn.microsoft.com/en-us/windows/apps/publish/store-policies#1116-live-generative-ai-content`.

This PRD addresses the desktop product and certification portions. The companion backend PRD defines ingestion, review, audit, retention, and operator action.

## 3. Problem

### 3.1 There is no reporting action on AI output

AI Chat V2 renders assistant text and generated images in `AiChatV2Message.vue`. It provides message identity (`message.id`), conversation identity (`message.conversationId`), model metadata, and output content, but no report control.

Legacy `AiChatBox.vue` and knowledge chat also render assistant messages. Knowledge chat currently offers Copy, Regenerate, and Like actions, but no report action.

AI-generated email templates, artifacts, keywords, plans, and automated replies can also be presented to users outside a chat bubble. A Chat-V2-only solution would leave secondary generative surfaces non-compliant.

### 3.2 Existing feedback and crash reporting do not meet the requirement

Plan approval feedback asks an AI model to revise a plan. A thumbs-up action records preference. Crash reporting submits software diagnostics. None of these explicitly reports inappropriate AI-generated content to a developer review queue.

Reusing the crash-report control would also be misleading. Crash uploads have different consent, payload, retention, rate-limit, and operator-review semantics.

### 3.3 A decorative button is insufficient

The Store policy requires the developer to take appropriate action based on reported concerns. The desktop therefore needs a live backend path, clear delivery confirmation, stable report identifiers, retryable failures, and certification instructions that a reviewer can execute.

### 3.4 Report evidence can contain private data

AI output may include personal information, generated credentials, copied customer data, proprietary text, or an image derived from a private prompt. The app must send enough evidence for review without silently attaching prompts, reasoning, files, tool arguments, workspace data, or conversation history.

## 4. Goals

1. Every accessible user-visible AI output has an obvious in-product reporting action.
2. A user can submit a report in no more than three interactions after selecting the report action: choose category, optionally add context, submit.
3. The report contains enough bounded evidence for a human reviewer to understand the concern.
4. The user knows exactly what will be transmitted before submission.
5. Report submission remains available independently of AI entitlement and model availability.
6. A successful submission returns and displays a stable `air_...` report identifier.
7. Failed submissions preserve the user's selections and can be retried.
8. All user-facing reporting copy is translated into English, Chinese, Spanish, French, German, and Japanese.
9. The feature is accessible by keyboard and screen reader and works at Microsoft Surface Laptop display sizes.
10. Store metadata, Partner Center disclosure, screenshots, and certification notes demonstrate compliance with Policy 11.16.

## 5. Non-Goals

1. Do not build a general customer-support ticket system in the desktop app.
2. Do not add public comments, social moderation, or user-to-user reporting.
3. Do not let the reporting action ask the model to regenerate or revise content.
4. Do not automatically submit reports based only on local content classification.
5. Do not upload a user's prompt, full conversation, reasoning trace, attachments, workspace files, browser content, email inbox, or tool results unless that exact item is the selected AI output.
6. Do not store report records in the desktop SQLite database. The backend is the report source of truth.
7. Do not require an active paid plan to submit a report.
8. Do not create an offline report queue in v1. A failed network request remains in the open dialog for manual retry.
9. Do not promise that a reporter will receive an individual response or remediation outcome in v1.
10. Do not remotely delete historical output from a user's local chat database in v1.

## 6. Users and Stakeholders

| User or stakeholder | Need |
| --- | --- |
| AiFetchly user | Report an AI response or image that is harmful, illegal, deceptive, private, or otherwise inappropriate. |
| Microsoft Store reviewer | Find and successfully test the reporting action without hidden navigation or special configuration. |
| Support and safety reviewer | Receive a stable report with enough evidence and source metadata to triage it. |
| Product and AI engineering | Identify recurring failures by surface, model, category, and app version without logging report content. |
| Privacy owner | Ensure users understand transmission and that unrelated private context is excluded. |
| Localization and accessibility reviewers | Verify equivalent reporting behavior across supported languages and input methods. |

## 7. Product Principles

1. **Put the action next to the output.** A global support page is not a substitute for identifying the specific generated item.
2. **Report what the user selected, not the conversation around it.** Evidence is explicit and bounded.
3. **Consent before transmission.** The dialog states what will be sent and does not rely on a buried privacy-policy link.
4. **Safety reporting is not paywalled.** Use a normal validated IPC handler, not the hosted-AI entitlement wrapper.
5. **One contract across surfaces.** Chat, images, artifacts, plans, and editors use a shared component and typed report request.
6. **Confirmation must be inspectable.** Success includes a report identifier that users and Store reviewers can record.
7. **Operational truth beats UI theater.** The action ships only when the backend review queue is live.

## 9. User Journeys

### 9.1 Report an inappropriate text response

1. User receives a completed assistant response.
2. User selects **Report AI output** below the response.
3. A dialog identifies the output as an AI response and shows a short read-only preview.
4. User selects a category and optionally enters an explanation.
5. Dialog states that the displayed AI response and explanation will be sent; prompts, other messages, files, and reasoning will not be included.
6. User selects **Submit report**.
7. App displays: “Report submitted. Reference: `air_...`.”
8. The action is disabled for that output for the remainder of the session and labeled **Reported**.

### 9.2 Report a generated image

1. User selects **Report AI output** on an assistant message containing generated images.
2. Dialog shows thumbnails with each image selected by default.
3. User may deselect unrelated images when the assistant message contains multiple images, but at least one output item must remain selected.
4. The app creates bounded previews. It never sends local file paths or signed remote URLs as the evidence itself.
5. Submission and confirmation follow the text flow.

### 9.3 Report from an editor

1. AI generates an email template or keyword set.
2. The generated result area shows **Report AI output** before Save, Apply, or Send actions.
3. The report snapshot captures the generated version currently displayed, not later user edits.
4. The editor remains open after submission; reporting does not discard work.

### 9.4 Submission fails

1. User selects Submit.
2. Network, authentication, rate-limit, or server failure occurs.
3. Dialog stays open with category, note, and selected evidence intact.
4. App displays a localized safe error and a **Try again** action.
5. A 429 response states that too many reports were submitted and asks the user to retry later; it does not repeatedly auto-retry.

### 9.5 AI entitlement changed

1. User opens a historical AI response after a paid plan expires or hosted AI is disabled.
2. Report action remains available.
3. Submission uses current optional authentication identity but does not call the model or require `USER_AI_ENABLED`.

## 11. UX and Accessibility Requirements

1. The report action must meet WCAG 2.1 AA contrast and focus-indicator requirements.
2. Keyboard users can focus the action, open the dialog, select a category, enter a note, submit, and close without a pointer.
3. Opening the dialog moves focus to its heading or first field. Closing returns focus to the originating output action.
4. Screen readers announce the action as “Report this AI-generated output,” followed by output type when useful.
5. Category errors and submission errors use text and ARIA live announcements, not color alone.
6. Image thumbnails have localized alt text and selected state.
7. Dialog works at 1,366×768 and 200% Windows scaling without hiding Submit or Cancel.
8. User-visible strings use `t()` with an English fallback and matching keys in all six supported language files.
9. Do not use `window.alert` for the main reporting flow. Use Vuetify dialog/snackbar components with controlled focus.

## 12. Shared Data Contract

The desktop and backend PRDs use this contract. Implementation may add optional backward-compatible fields but must not change required field meaning without updating both PRDs.

### 12.1 Enums

```typescript
type AIContentReportCategory =
  | "hate_or_harassment"
  | "sexual_content"
  | "violence_or_self_harm"
  | "child_safety"
  | "illegal_or_dangerous"
  | "privacy_or_personal_data"
  | "misinformation_or_deception"
  | "copyright_or_ownership"
  | "other";

type AIContentType =
  | "text"
  | "image"
  | "mixed"
  | "plan"
  | "artifact"
  | "email_template"
  | "keyword_set";

type AIOutputSurface =
  | "chat_v2"
  | "legacy_chat"
  | "knowledge_chat"
  | "ai_artifact"
  | "email_template_editor"
  | "keyword_generator"
  | "automatic_email_reply"
  | "other";
```

### 12.2 Request

```typescript
interface CreateAIContentReportRequest {
  schemaVersion: 1;
  clientReportId: string;       // UUID generated once when dialog opens
  surface: AIOutputSurface;
  contentType: AIContentType;
  category: AIContentReportCategory;
  comment?: string;             // max 2,000 chars
  output: {
    text?: string;              // max 32,000 chars
    textTruncated?: boolean;
    imagePreviews?: Array<{
      mimeType: "image/jpeg" | "image/webp" | "image/png";
      dataBase64: string;        // max 1 MiB decoded each, max 3
      width: number;
      height: number;
      sha256?: string;
    }>;
    evidenceUnavailable?: boolean;
  };
  context: {
    conversationId?: string;    // max 128
    messageId?: string;         // max 128
    artifactId?: string;        // max 128
    model?: string;             // max 128
    generatedAt?: string;       // RFC3339
    appVersion: string;         // max 64
    platform: "win32" | "darwin" | "linux";
    locale: string;             // BCP 47, max 32
  };
}
```

At least one of `output.text`, `output.imagePreviews`, or `output.evidenceUnavailable` must be present. `evidenceUnavailable` alone is accepted only when `comment` is non-empty.

### 12.3 Response

```typescript
interface CreateAIContentReportResponse {
  reportId: string;             // air_<server-generated token>
  status: "submitted";
  receivedAt: string;           // RFC3339
  duplicate: boolean;           // true when clientReportId already existed
}
```

The normal Electron IPC envelope remains `{ status, msg, data }`; `data` contains the response above.

## 13. Product Architecture Constraints

### 13.1 Proposed desktop modules

```text
src/entityTypes/aiContentReportTypes.ts
src/schemas/ipc/aiContentReport.ts
src/service/AIContentReportService.ts
src/main-process/communication/ai-content-report-ipc.ts
src/views/api/aiContentReport.ts
src/views/components/aiContentReport/AIContentReportButton.vue
src/views/components/aiContentReport/AIContentReportDialog.vue
```

The shared UI component owns presentation and user selection. The service owns evidence normalization and remote submission. IPC validates and delegates. `AiChatApi` or a small remote API adapter may own the HTTP method, but the report handler must not invoke model selection, billing reservation, or the AI feature gate.

### 13.2 Integration rules

- Components pass stable identifiers and the selected generated snapshot into the shared report UI.
- `AiChatV2Message.vue` emits/report-handles assistant text, images, and history plan messages.
- Pinned plan cards expose the same action before approval.
- Artifacts report the generated snapshot or bounded plaintext representation, never executable HTML, scripts, or a live `file://` reference.
- Email-template reports capture the generated version before subsequent manual edits. If provenance is lost, the report action is hidden rather than mislabeling user-authored content as AI output.
- Keyword sets capture the generated list as text.
- The service generates `clientReportId` once and reuses it until success or dialog cancellation.

## 14. Privacy and Security Requirements

1. The dialog notice is explicit consent for sending the selected evidence.
2. No report is submitted in the background or on Like/Dislike.
3. Report content must never be printed to renderer console, main-process logs, analytics, crash reports, or error messages.
4. Logs may contain `clientReportId`, backend `reportId`, surface, category, app version, HTTP result, and duration. They must not contain output text, comments, image bytes, conversation content, raw user ID, or auth tokens.
5. Escape all text previews and never execute artifact HTML as part of the dialog.
6. Image conversion must reject SVG, HTML, unsupported data URLs, and files outside the exact generated-image metadata selected by the user.
7. The report channel accepts only validated plain data. It cannot accept arbitrary filesystem paths or URLs.
8. Use existing token refresh behavior for authentication. If no user token is available, backend anonymous identity rules apply.
9. Reporting remains available when `USER_AI_ENABLED !== "true"`; this exception grants no AI generation capability.
10. Update the public privacy policy before Store resubmission.

## 15. Analytics and Diagnostics

Allowed events:

| Event | Allowed properties |
| --- | --- |
| `ai_content_report_opened` | surface, contentType, appVersion |

## 18. Test Plan

### 18.1 Unit tests

- Zod accepts every valid category/content/surface combination and rejects unknown keys.
- Text truncation preserves beginning/end and sets `textTruncated`.
- Image evidence rejects unsupported MIME, oversize decoded bytes, too many images, invalid dimensions, paths, and URLs.
- Request construction excludes prompts, reasoning, attachments, tool arguments, and neighboring messages.
- Same dialog submission reuses `clientReportId` after timeout/failure.
- Safe error mapping covers 400, 401/403, 413, 429, 503, network, and unknown errors.

### 18.2 Component tests

- Action appears only on completed reportable AI output.
- Dialog requires a category and valid evidence.
- Cancellation sends nothing.
- Submit disables while in flight.
- Failure retains fields and enables retry.
- Success displays exact report ID and marks output Reported for the session.
- Plan-card and image-only message branches expose the action.
- Keyboard focus enters and returns correctly.

### 18.3 IPC/main-process tests

- Preload allowlist permits only the report invoke channel needed by renderer.
- Handler validates before network access.
- Handler uses the non-AI validated wrapper and works with `USER_AI_ENABLED=false`.
- Handler does not touch TypeORM or desktop database models.
- Authorization stays in main process.
- Backend duplicate response is treated as success.

### 18.4 Integration tests

- Chat V2 text report reaches a stub backend with exact bounded payload.
- Generated-image report sends the re-encoded preview and no local path.
- Historical message can be reported after AI entitlement is disabled.
- Anonymous/local-provider session follows backend anonymous rules.
- Rate-limit response preserves dialog data.
- All six locales render without missing keys.

### 18.5 Windows Store certification test

Test on a Microsoft Surface Laptop class device or equivalent Windows environment:

1. Install the exact Store package.
2. Sign in with the certification account.
3. Open AI Assistant and submit a benign test prompt.
4. Wait for generation to complete.
5. Select **Report AI output** beneath the response.
6. Choose **Other**, enter “Microsoft certification test,” and submit.
7. Verify success and record the `air_...` reference.
8. Confirm the report appears in the authenticated admin queue with matching category, surface, app version, and bounded evidence.
9. Repeat with a generated image if image generation is exposed to the reviewer account.

## 19. Acceptance Criteria

The feature is ready for Store resubmission only when all conditions are true:

1. Every P0 surface accessible in the submitted package has a per-output report action.
2. Any accessible P1 surface either has the action or is disabled in the submitted package with documented rationale.
3. Dialog uses explicit consent, bounded evidence, and all six language packs.
4. No prompt, reasoning, file, tool argument, or unrelated message is transmitted.
5. `POST /api/ai/content-reports` is live in the certification environment.
6. A valid report returns and displays an `air_...` identifier.
7. Duplicate manual retry with the same `clientReportId` does not create a second report.
8. Backend admin can view, triage, and record an action on the report.
9. Reporting works with hosted AI disabled and does not consume credits.
10. Unit, component, IPC, integration, localization, accessibility, and certification tests pass.
11. Store metadata and Partner Center disclose live generative AI.
12. Privacy policy describes AI-content reporting.

- [ ] Screenshots attached to submission notes.
- [ ] Submitted test report reviewed and action recorded.

## 21. Risks and Mitigations

| Risk | Mitigation |
| --- | --- |
| Reviewer cannot find an icon-only action | Use icon plus visible **Report AI output** text on primary chat surfaces. |
| Secondary AI surface causes another rejection | Complete the surface audit; add reporting or disable that surface in the Store build. |
| Report leaks prompts or workspace data | Construct an allowlisted snapshot from the selected output only; test excluded fields. |
| Image payload is too large | Re-encode, resize, cap count and bytes, and allow comment-only fallback when evidence conversion fails. |
| Retry creates duplicates | Generate one client UUID per dialog and enforce backend idempotency. |
| Expired subscription blocks safety flow | Use the normal validated IPC wrapper and no AI entitlement check. |
| Button exists but backend is unavailable | Store gate requires a live ingestion and admin-review smoke test before submission. |
| Report content appears in logs | Metadata-only logging and automated log-capture tests. |
| Translation omission | CI parity check across all six language files. |

## 22. Final Product Decision

AiFetchly will provide a report action directly on every accessible user-visible AI output. Reports will transmit only the selected bounded output and the reporter's optional explanation, through main-process IPC to a dedicated backend queue. The feature will remain available independent of AI entitlement, will return a stable reference, and will ship together with an operational admin review flow and complete Microsoft Store disclosure evidence.
